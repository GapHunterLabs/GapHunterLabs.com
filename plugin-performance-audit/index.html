Plugin performance audit

For teams that ship an IntelliJ Platform plugin and hear about UI freezes, typing lag or high CPU. One plugin, a fixed scope and a fixed price, with written results and patches.

Ask for a quote Email me

How do you diagnose a performance bottleneck in an IntelliJ IDEA plugin?

I reproduce the plugin in a clean IDE for each version it supports, with freeze detection on and thread dumps captured on every freeze, then measure the time spent on the UI thread when settings pages, actions and tool windows open, cold and warm. In the code review I look for the freeze patterns behind most reports in the JetBrains tracker: blocking read actions in background tasks without cancellation, file or network access on the UI thread, and waits on other threads while holding the read lock. I trace every finding to the exact code that caused it. I report what I find; I cannot prove that no other freeze exists.

How do you prove a performance fix actually works?

Each patch I propose comes with a before and after measurement of the same action on the same IDE version, so the improvement is a number you can check, not a claim. I deliver patches as a pull request or a diff with tests where the fix allows them. It is the same method I used on freezes in IntelliJ's own code, which I reported to JetBrains with a root cause and a measurement.

Who it is for

  • Plugin vendors whose reviews or support inbox mention freezes, "IDE is not responding", slow typing or high CPU.
  • Companies with an internal plugin that their developers complain about.
  • Teams preparing a release for a new IDE version who want the cost on the UI thread measured before users see it.

What the audit covers

  • Reproduction. I run your plugin in a clean IDE for each version you support, with freeze detection set to 500 ms and thread dumps captured on every freeze.
  • UI thread measurements. I measure the time spent on the UI thread when your settings page opens, when your actions update, when your tool windows open and at startup, each time cold and warm.
  • Code review for freeze patterns. I look for blocking read actions in background tasks without cancellation, file or network access and process launches on the UI thread, and waits on other threads while holding the read lock. These patterns are behind many of the freeze reports in JetBrains' issue tracker.
  • Your existing reports. I trace the thread dumps or idea.log excerpts that users already sent you to the code that caused them.

What you receive

  • A written report: each finding with its measurement or stack trace, why it blocks and its priority.
  • Proposed patches as a pull request or a diff, with tests where the fix allows them.
  • Before and after measurements for every finding that gets a patch.
  • One round of follow-up questions by email after delivery.
