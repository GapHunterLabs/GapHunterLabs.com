Engineering & Evidence

JetBrains Platform tickets

Bugs in JetBrains’ own code, documented publicly in JetBrains’ YouTrack tracker: six filed directly, four found in IntelliJ’s source by a check from this catalog or a related scan and two by measuring the Settings pages on the UI thread, plus root-cause analysis posted on existing IntelliJ Platform (IJPL) tickets, and eight pull requests to intellij-community, one already merged into master.

Filed directly

Bugs found in IntelliJ’s own source by a check from this catalog or by measuring the IDE’s UI thread, then reported to JetBrains.

IDEA-393501 ↗

SearchForTestsTask: non-cancellable ReadAction.run() in a background task

Fixed
IntelliJ IDEA

I found it with Background ReadAction Freeze Companion. SearchForTestsTask is a Task.Backgroundable whose run() wrapped search() in the cancellable ReadAction.nonBlocking(), then called the sibling onFound() through the blocking ReadAction.run() a few lines later, with no checkCanceled() anywhere in the class. JetBrains’ Platform Blog names this pattern as a recurring cause of UI freezes. I filed it as IJPL-254654; JetBrains moved it to the IDEA project (Java › Tests) and assigned it to a developer.

In a follow-up comment (October 2026) I added two points. The default smart-mode branch also blocks: it calls the deprecated DumbService.runReadActionInSmartMode(), which uses ReadAction.computeBlocking() internally. And a plain switch to ReadAction.nonBlocking() is not safe, because onFound() writes files and a restarted read action would write them again. JetBrains fixed it on master on October 28, 2026 (commit 4a88fdfa): onFound() now runs in a non-blocking read action in smart mode, the loops that build the test lists call checkCanceled(), and the JUnit upload step moved to onSuccess(). The ticket is marked Fixed.

IJPL-257836 ↗

DependenciesUsagesPanel.findUsages runs the whole dependency usage search in one non-cancellable read action

Open
IntelliJ Platform

I found it with the same check as Background ReadAction Freeze Companion, which I ran as a scan over IntelliJ’s own master. When a node is selected in the Dependency Viewer (Code › Analyze Code › Dependencies), DependenciesUsagesPanel.findUsages() analyzes every file of the selected scope inside one top-level ReadAction.runBlocking() on a pooled thread. A pending write action, such as typing in an editor, waits until the whole search ends. In the ticket I propose the fix shape JetBrains used for IJPL-236316 (FindUsagesHelper): a non-blocking read action that no longer swallows ProcessCanceledException, with the UI update moved out of the read action. JetBrains support asked for reproduction steps. I wrote a headless test on a synthetic project that reproduces it: with 2,000 files, a write action waited 4.8 s for the search, and 1 ms with a non-blocking read action. I attached the test to the ticket and proposed a fix in pull request #3684.

IJPL-257854 ↗

Auto-test: the error check of DelayedDocumentWatcher blocks typing until the whole check ends

Open
IntelliJ Platform

I found it with the same check, during an audit of components that do background work after each edit. With auto-test enabled, DelayedDocumentWatcher waits for a typing pause and then checks every changed file for syntax errors (PsiErrorElementUtil.hasErrors()) in one blocking read action on a pooled thread. The keystroke that resumes typing waits for the whole check. I measured it with the platform test framework on IntelliJ IDEA 2025.2: on a 50,000-line file, that keystroke took 436 ms with the current code, 48 ms without auto-test, and 73 ms with the check in a non-blocking read action. I attached the measurement test to the ticket and proposed a fix in pull request #3685.

IJPL-257908 ↗

Live Templates settings: isModified() checks every template against every context type on the EDT after each click or key press

Open
IntelliJ Platform

I found it by measuring every Settings page on the UI thread of IntelliJ IDEA 2026.2.3 with the platform test framework. The Settings dialog calls isModified() of the open page about one second after each mouse click or key press. On the Live Templates page, that call compares all 1,295 templates against all 336 context types (TemplateContext.getDifference()), and the UI thread stops for about 165 ms each time. In the ticket I propose a one-line check: two templates whose own context settings are equal cannot differ in any context type. In the same test, that check takes the comparison from 157 ms to 0 ms with the same result. I attached the measurement test to the ticket.

IJPL-257909 ↗

Settings | Plugins: isRequiredForEssentialPlugin rebuilds the plugin maps and walks all essential dependencies once per plugin on the EDT

Open
IntelliJ Platform

I found it in the same measurement of the Settings pages. Opening Settings › Plugins builds the list of installed plugins on the UI thread and asks, for each plugin, whether an essential plugin requires it. Each answer builds the plugin and module maps again and walks the dependencies of every essential plugin; the source code already has a FIXME about it. With 158 plugins loaded, the page took 689–931 ms to open. One walk followed by a lookup per plugin took 8–22 ms and gave the same answer for every plugin. The cost grows with the square of the number of installed plugins. I attached the measurement test to the ticket.

IJPL-257919 ↗

Package File: PackageFileWorker does all the file I/O inside one blocking read action, so write actions wait for it

Fixed
IntelliJ Platform

I found it by scanning IntelliJ’s own master for slow work inside read actions, and then measured it. Build › Package File copies a file into the artifacts that contain it. PackageFileWorker finds those artifacts and then does all the file I/O inside the same blocking ReadAction.run(): the copy, opening the archive, and repacking a nested archive. A write action requested meanwhile, such as a key press, waits until the I/O ends. I measured it with the platform test framework on IntelliJ IDEA 2026.2.3, with a WAR that contains a 40 MB JAR: the write action waited 2,219–2,508 ms. With only the artifact lookup in the read action and the I/O outside it, it waited 0 ms in 4 of 4 runs. I attached the measurement test to the ticket.

Fixes contributed

Pull requests I sent to JetBrains’ intellij-community repository — fixes for the bugs reported above, plus new and extended Java inspections contributed to the platform.

PR #3684 ↗

IJPL-257836 Dependency Viewer: run the usage search in a non-blocking read action

Open
GitHub

Fix for IJPL-257836. The usage search runs in ReadAction.nonBlocking(...), which restarts when a write action is pending, the same fix shape JetBrains used for IJPL-236316. The search has no side effects, so a restart is safe, and the usage view is built after the read action. A new test holds the search inside its read action and checks that a write action does not wait for it. Against the IntelliJ IDEA 2025.2 jars, the write action waited 10,021 ms with the current code and 3 ms with the fix. I did not run the test inside the full intellij-community build.

PR #3685 ↗

IJPL-257854 Auto-test: check changed files for errors in a non-blocking read action

Open
GitHub

Fix for IJPL-257854. The error check runs in ReadAction.nonBlocking(...), which restarts when a write action is pending; hasErrors() has no side effects, so a restart is safe. The changed files are copied before the check, because the set is used on the EDT. I measured it against the IntelliJ IDEA 2025.2 jars with a copy of the patched class: the keystroke that resumes typing on a 10,000-line file took 134 ms with the current code and 25 ms with the fix. I did not build the change inside the full intellij-community build.

PR #3694 ↗

IJPL-257908 Live Templates: fast path in TemplateContext.getDifference

Open
GitHub

Fix for IJPL-257908. Live Templates recomputed isModified() on the EDT after every click or keystroke (~165 ms on the measured setup). A one-line fast path in TemplateContext.getDifference brings that to ~0 ms. The equivalence is measured in a repro harness; the inspection test is run by JetBrains’ CI.

PR #3696 ↗

IJPL-257919 Package File: keep the file I/O outside the read action

Merged
GitHub

Fix for IJPL-257919. Build › Package File now resolves the target artifacts under a small ReadAction.compute(), but the file I/O (copying, opening and rewriting the ZIP, re-packing a nested archive) runs outside the read lock, so a write action no longer waits for it. The existing PackageFileActionTest covers the functional result; the timing measurement is attached to the ticket. JetBrains merged the change into master, with a follow-up that removed a deprecated-method call.

PR #3701 ↗

IJPL-257909 Plugins settings: cache the essential-plugin requirement set

Open
GitHub

Fix for IJPL-257909. The Plugins settings page recomputed, for every plugin, whether it is required by an essential plugin (a FIXME in the source). The fix caches that set per PluginSet instance, invalidated structurally when the plugin set is replaced. Functional equivalence was reconfirmed across the catalog of descriptors (158/158).

PR #3697 ↗

IDEA-266545 New Java inspection: magnitude comparison of System.nanoTime()

Open
GitHub

For IDEA-266545. A new Java inspection (Probable bugs, off by default) flags < > <= >= comparisons where an operand is a direct System.nanoTime() call; the correct subtraction idiom is not flagged. Detection logic verified locally against 2026.2.3; the inspection test runs in JetBrains’ CI.

PR #3698 ↗

IDEA-279282 Simplifiable Map operations: suggest map.remove(key, value)

Open
GitHub

For IDEA-279282, an extension of the existing ‘Simplifiable Map operations’ inspection, where a JetBrains maintainer asked for it. It detects if (value.equals(map.get(key))) map.remove(key) (both operand orders) and offers map.remove(key, value), guarding against a null value and side-effecting key/value expressions.

PR #3699 ↗

IDEA-279659 New Java inspection: String.compareTo() used for equality

Merged
GitHub

For IDEA-279659. A new Java inspection (Verbose or redundant code, off by default) flags compareTo(...) == 0 / != 0 on strings and offers equals() / !equals(), restricted to String and guarded against the null-argument difference (compareTo(null) throws, equals(null) is false). Detection and quick-fix verified locally. JetBrains integrated the change into master on October 30, 2026.

Analysis on existing tickets

Root-cause comments I posted on open IntelliJ Platform tickets. Most come from reading the current source on master; the comment on IJPL-223452 adds a headless reproduction.

IJPL-200871 ↗

CME in workspace model

Fixed
IntelliJ Platform

WorkspaceFileIndexDataImpl.fillPackageFilesAndDirectories() iterates an unsynchronized LinkedHashMap that can change mid-iteration, producing a ConcurrentModificationException. The analysis I posted here located that iteration, and I proposed a ProgressManager.checkCanceled() call. JetBrains fixed the ticket on 2026-09-09 with a different change: the package-name queries now call ensureIsUpToDate() before reading, so the index is brought up to date first (commit e1d600df).

IJPL-27359 ↗

CME in InspectionToolRegistrar.createTools on loading/unloading plugins

Submitted
IntelliJ Platform

toolFactories is iterated as a live, unsynchronized view of a mutable map inside createTools(), running on background threads with no read-action lock, so a concurrent plugin unload can mutate the map mid-iteration. The same live view is still on master (now in Kotlin), so the 2020 failure looks reproducible under the same conditions.

IJPL-80817 ↗

Cannot create light service git4ide.repo.GitRepositoryManager because container is already disposed

Submitted
IntelliJ Platform

The original call site moved after a widget restructuring, but the repository lookup still runs under the deprecated runInReadActionWithWriteActionPriority, and none of the utility functions in the new chain (GitBranchUtil, DvcsUtil, GitUtil) call checkCanceled(), so a project closing can still race into an AlreadyDisposedException, with a narrower window than when it was reported.

IJPL-76141 ↗

Git Log is empty due to a StackOverflow exception in IntToIntBtree.processLeafPages

Open
IntelliJ Platform

processLeafPages recurses with no stack-depth guard, so a large enough index overflows the stack and silently empties Git Log. The same method fails in IJPL-250279, reported independently about a year later for the JPS build cache; the two tickets had not been linked. I propose rewriting the traversal iteratively.

IJPL-196254 ↗

Memory leak via ProjectRootManagerImpl::rootsChanged

Open
IntelliJ Platform

BatchSession's changes list only clears once its pendingRootsChanged counter hits exactly 0, but the counter is incremented without matching exception handling, so one exception or an asymmetric reentrant call can leave it stuck above 0 permanently, and changes then keeps growing on every later roots-changed event. The missing safety net is visible in the code; I did not trace the exact first imbalance.

IJPL-223452 ↗

PsiSmartPointer improvements

Open
IntelliJ Platform

I posted a comment with a headless reproduction of slow typing in large files. With the Structure tool window built for a Java file with 10,000 methods, the file holds 10,001 smart pointers, one per tree node (PsiTreeAnchorizer). After each keystroke the IDE restores every pointer: in IntelliJ IDEA 2026.2.3 a keystroke took a median of 1,080 ms, against 33 ms without the structure view, with 98% of the time in SmartPsiElementPointerImpl.doRestoreElement(). This matches the slow typing events reported in IJPL-173280. I attached the test to the comment.
